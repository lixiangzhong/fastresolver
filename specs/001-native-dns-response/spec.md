# Feature Specification: Native DNS Response

**Feature Branch**: `refactor/native-dns-response`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: "看一下这个项目代码，起一个分支用来重构，保留现在的 resolver 的接口抽象设计，把 DNSRR 的返回改成 dns 库原生的 *Response, error"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 获取完整原生 DNS 响应 (Priority: P1)

作为解析器调用方，我希望每次查询直接获得 DNS 库的原生响应对象，以便读取答案区、权威区、附加区、响应码和协议标志等完整信息，不再受自定义聚合结果字段的限制。

**Why this priority**: 这是本次重构的核心价值；只有统一返回原生响应，调用方才能无损使用 DNS 协议数据并避免项目维护第二套响应模型。

**Independent Test**: 使用包含 Answer、Authority、Additional、响应标志和多种记录类型的可控 DNS 响应执行一次查询，验证调用方收到的对象完整保留所有响应内容。

**Acceptance Scenarios**:

1. **Given** 上游返回包含多个 DNS 区段和记录类型的有效响应，**When** 调用方通过解析器抽象执行查询，**Then** 返回对象完整保留上游 DNS 响应的区段、记录、响应码和协议标志。
2. **Given** 上游返回 NXDOMAIN 或其他合法 DNS 响应码，**When** 查询完成且传输与解析过程无故障，**Then** 调用方能够从原生响应中读取该响应码，现有错误语义不被无意改变。
3. **Given** 查询因网络、超时、响应解码或上游拒绝策略而失败，**When** 解析器返回，**Then** 调用方获得可判定的错误，且在上游响应已经可用时不会丢失该响应对象。

---

### User Story 2 - 保持解析器组合方式 (Priority: P2)

作为库使用者，我希望继续通过统一的解析器接口组合基础解析器、重试、超时、限流、缓存、负载均衡、并发竞速、熔断、回退、CNAME 跟随和递归解析能力，而无需改变现有构建方式。

**Why this priority**: 当前项目的主要设计价值来自统一接口和装饰器组合；返回类型迁移不能破坏这套抽象。

**Independent Test**: 分别构造每一种现有解析器及一条包含多个装饰器的组合链，通过同一接口发起查询，验证所有实现均返回相同种类的原生响应对象并保持各自职责。

**Acceptance Scenarios**:

1. **Given** 调用方已有一条由多个解析器装饰器组成的链，**When** 将代码迁移到新返回契约，**Then** 解析器的创建、包装顺序和查询入参保持不变。
2. **Given** 任一装饰器收到成功响应，**When** 它执行缓存、重试判定、统计或结果转发，**Then** 返回的原生响应内容不被降级为自定义聚合对象，也不发生非职责范围内的修改。
3. **Given** 自定义实现满足统一解析器接口，**When** 其返回类型迁移到新的原生响应对象，**Then** 它仍可被所有现有装饰器接受和组合。

---

### User Story 3 - 迁移现有调用方 (Priority: P3)

作为项目维护者，我希望仓库内的示例、测试和内部解析流程全部使用同一原生响应契约，以便删除不再需要的自定义 DNS 结果模型和转换逻辑，避免形成两套事实来源。

**Why this priority**: 完整迁移可确保公共接口、内部实现和使用示例一致，降低后续维护与协议字段遗漏风险。

**Independent Test**: 检查仓库内所有生产代码、测试和示例，确认不再通过 `DNSRR` 或其专用字段读取解析结果，并验证完整测试套件通过。

**Acceptance Scenarios**:

1. **Given** 仓库内存在依赖 `DNSRR` 专用字段的递归、缓存、CNAME 和示例代码，**When** 重构完成，**Then** 这些调用方直接依据原生 DNS 响应的标准区段和字段完成原有行为。
2. **Given** 原有自定义结果类型及转换函数已无调用方，**When** 检查公共代码，**Then** 不再保留作为替代返回路径的重复响应模型或隐藏兼容分支。
3. **Given** 下游使用者阅读迁移说明，**When** 修改其结果读取和自定义解析器实现，**Then** 无需改变解析器构建方式和查询参数即可完成迁移。

### Edge Cases

- 上游返回空响应对象、无法解码的响应或缺少 Question 区段时，查询必须返回明确错误且不得发生崩溃。
- UDP 响应被截断并切换到 TCP 时，最终返回对象必须是 TCP 的完整响应，而非先前的截断对象。
- NXDOMAIN、空 Answer 但带 Authority/SOA、REFUSED、SERVFAIL 等响应必须保留原始响应码和可用区段；错误行为须与既有契约一致，除非迁移文档明确列为变更。
- 并发竞速在所有解析器失败、响应与错误同时到达、调用上下文取消时，必须稳定结束且不返回无效的空成功结果。
- 缓存中的响应不得因调用方修改返回对象而污染后续查询结果；缓存命中与未命中必须提供等价的响应内容。
- CNAME 链循环、超过深度限制或中间响应缺少目标记录时，必须保留现有终止和错误行为。
- JSON DNS 服务无法直接提供线格式响应时，转换结果必须保留该服务实际返回的所有可表达 DNS 字段，不得伪造缺失数据。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 保留现有统一解析器接口的职责、查询方法、上下文参数、查询名称参数和查询类型参数，仅迁移查询结果契约。
- **FR-002**: 所有解析器实现 MUST 继续使用 `github.com/miekg/dns`，并统一返回该库的原生 `*dns.Msg` 响应与错误。
- **FR-003**: 基础 UDP/TCP 解析、DoH 解析和 JSON DNS 解析 MUST 生成同一种原生 DNS 响应对象，并保留来源可提供的 Question、Answer、Authority、Additional、响应码和协议标志。
- **FR-004**: 重试、超时、限流、缓存、负载均衡、并发竞速、指标、熔断和回退装饰器 MUST 继续接受统一解析器接口，并透明传递原生响应对象。
- **FR-005**: CNAME 跟随和递归解析 MUST 直接基于原生响应区段与记录进行判断，在迁移后保持现有查询终止、委派、权威响应和错误行为。
- **FR-006**: 缓存 MUST 根据原生响应中的 DNS TTL 信息维持动态过期行为，并隔离缓存值与调用方可变对象，防止跨查询数据污染。
- **FR-007**: 系统 MUST 保持既有网络错误、上下文取消、超时、熔断、无可用解析器、递归深度和上游拒绝等错误可判定性。
- **FR-008**: 对于已经获得的非成功 DNS 响应，系统 MUST 在返回错误时尽可能同时返回原生响应，以便调用方检查响应码和区段。
- **FR-009**: 仓库内所有解析器实现、装饰器、自定义测试解析器、示例和内部调用 MUST 迁移到新的统一返回契约。
- **FR-010**: 不再承担公共或内部职责的 `DNSRR`、其专用子类型和转换逻辑 MUST 被移除，系统 MUST NOT 保留隐藏的双重返回模型或自动降级路径。
- **FR-011**: 项目 MUST 提供清晰的破坏性变更说明，列出返回类型、自定义解析器实现、结果字段读取方式和被移除类型的迁移要求。
- **FR-012**: 所有可控解析器测试 MUST 使用本地或确定性响应，且覆盖成功、DNS 非成功响应码、传输失败、上下文取消、截断回退和响应对象隔离。

### Key Entities

- **Resolver abstraction**: 所有基础解析器和装饰器共同遵守的查询契约；保留现有组合边界，只改变查询结果类型。
- **Native DNS response**: 单次 DNS 查询得到的完整协议响应，包含问题、答案、权威、附加区段以及响应码和协议标志。
- **Resolver decorator**: 在不改变响应模型的前提下提供缓存、重试、超时、限流、均衡、并发、指标、熔断或回退行为的组合组件。
- **Lookup error**: 描述传输、取消、超时、策略拒绝、响应解码或解析流程失败，并可与已经获得的 DNS 响应共同返回。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的现有解析器实现和装饰器通过同一个更新后的解析器契约返回原生 DNS 响应，且不保留第二种查询结果契约。
- **SC-002**: 在覆盖 Question、Answer、Authority、Additional、响应码和协议标志的确定性样例中，100% 的上游可用字段可由调用方从返回对象读取。
- **SC-003**: 所有现有解析器组合场景在迁移后保持可构建、可查询，并通过成功、失败和上下文取消测试。
- **SC-004**: 现有调用方迁移时只需调整结果读取方式和自定义解析器的返回签名；解析器构造参数、装饰器组合方式和查询入参无需改变。
- **SC-005**: 仓库的完整自动化测试、静态检查和示例构建全部通过，且网络敏感行为均有确定性验证覆盖。
- **SC-006**: 对同一可控 DNS 响应进行迁移前后对比时，既有递归、CNAME、缓存、重试、回退和错误判定用例的行为一致率达到 100%，明确批准的契约变化除外。

## Assumptions

- 本次是面向新主版本的破坏性 API 重构，不要求通过重载或并行接口维持 `DNSRR` 源码兼容性。
- “保留 resolver 的接口抽象设计”表示保留统一接口、`Lookup` 方法语义、查询入参以及装饰器组合模式，不表示保留原返回类型。
- 原 `DNSRR` 中的服务器地址、传输网络和往返耗时不是 DNS 协议响应字段；本次默认不在查询返回值中复制这些自定义元数据，也不额外引入新的结果包装类型。
- 除返回模型直接导致的必要调整外，重试次数、超时、缓存、负载均衡、熔断、CNAME 跟随和递归策略保持现有行为。
- `github.com/miekg/dns` 升级至 v1.1.73，`github.com/zonedb/zonedb` 升级至 v1.0.5780，最低 Go 版本提升至 1.25，统一以 `*dns.Msg` 作为查询响应类型。
- 该变更需要发布说明和版本升级提示，因为现有调用方和自定义 `ILookup` 实现无法在不修改源码的情况下继续编译。

## Scope Boundaries

- 本功能包含所有生产解析器、装饰器、内部流程、测试、示例和迁移文档的返回契约迁移。
- 本功能不新增解析协议、查询类型、解析策略或用户可配置项。
- 本功能不承诺保留 `DNSRR` 聚合字段或其子类型的源码兼容性。
- 本功能不借重构之机改变与返回模型无关的限流、均衡、熔断或递归算法。
